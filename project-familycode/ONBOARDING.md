# ONBOARDING — внедрение управляющей рамки в familycode

> Кому: ведущему (владельцу) проекта familycode.
> Что это: пошаговое внедрение готового набора файлов из этого каталога
> в ваш репозиторий. Пакет ничего не меняет в вашем проекте сам —
> все действия выполняете вы.

## 1. Зачем это: прямой ответ на ваш DEC-001

Вашим решением `DEC-001` (обязательный этап ведения документации и
контроля, статус approved) дальнейшая содержательная работа заблокирована,
а сам этап «ожидает вводных владельца проекта». Этот пакет и есть
кандидат в такие вводные. Соответствие условиям снятия блокировки
(DEC-001, раздел 5):

| Условие DEC-001 | Чем закрывается |
|---|---|
| 1. Владелец предоставляет вводные | этот пакет: правила, протокол сессий, гейты, память — на ваше решение |
| 2. Требования этапа зафиксированы | `FEDERATION-HOOK.md` + `AGENTS.md` (правила), протокол сессий, гейт кодификации |
| 3. Согласованные действия выполнены | шаги 3-6 ниже: файлы внедрены, гейт активирован, защита main включена |
| 4. Явное подтверждение владельца | ваша запись в `memory/decisionLog.md` (D-001 «принято») и — отдельно — ваше решение о снятии DEC-001 |

Важно: сам пакет DEC-001 не снимает. Снятие блокировки — только ваше
явное решение после выполнения этапа (DEC-001, раздел 5, пункт 4).

## 2. Что вы получаете

1. **Правила читают все инструменты.** `AGENTS.md` в корне понимают
   Codex, Cursor, VS Code/Copilot, Claude и другие; `CLAUDE.md` — дубль-
   подстраховка. Правила — в одном месте, адаптеры — только указатели.
2. **Протокол сессий.** Каждая сессия агента видна строкой в `SESSIONS.md`
   (кто, когда, в какой ветке, зачем); работа — в ветке
   `session/<дата>-<тема>`; в main — только через pull request.
3. **Механический контроль.** Локальный pre-commit гейт и тот же чек на
   GitHub (Actions на каждый PR): кодировки, BOM, пиктограммы,
   абсолютные пути. Правила держит инструмент, а не память людей.
4. **Память репозитория** (`memory/`): решения, активный контекст, заметки
   сессий — контекст переживает смену чатов, инструментов и людей.
   Слой дополняет ваш порядок (`docs/workbench`, статусы, PROJECT_CONTEXT),
   не заменяет его.

## 4. Активация гейта (одна команда, на каждом клоне)

Из корня репозитория:

```
git config core.hooksPath githooks
```

После этого каждый локальный commit проходит проверку кодификации
(LF, UTF-8, без BOM, без NUL, без пиктограмм и абсолютных путей вне
allowlist). Гейт проверяет только staged-файлы: исторические файлы
не трогаются, пока вы их не правите. Если при первой правке старого
файла гейт найдёт, например, CRLF — это нормально: либо исправить файл,
либо внести строку в `githooks/codification.allow` с записью-обоснованием
в `memory/decisionLog.md`.

## 5. Настройка GitHub (после первого пуша файлов)

1. Убедиться, что workflow лежит в `.github/workflows/codification-gate.yml`
   — он запускается на каждый pull request.
2. Settings -> Branches -> правило для main:
   - включить «Require a pull request before merging»;
   - включить «Require status checks to pass» и выбрать проверку
     `codification-gate` (появляется в списке после первого запуска).

С этого момента в main нельзя попасть мимо PR и мимо гейта.

## 6. Первое внедрение — обычным коммитом

Сами файлы рамки допустимо завести в main прямым коммитом (или одним PR),
ДО включения защиты ветки — это последняя «догейтовая» операция.
Рекомендуемый порядок: скопировать файлы -> активировать гейт (шаг 4) ->
закоммитить и запушить -> включить защиту (шаг 5).

## 7. Как выглядит первая рабочая сессия по протоколу

1. Строка в `SESSIONS.md` на main (до начала работы):
   `S-001 | <дата> | session/<дата>-<тема> | <цель> | <агент/инструмент> | <вы> | active`.
2. Создать ветку `session/<дата>-<тема>`, работать только в ней;
   каждый созданный артефакт коммитится сразу (сообщения — EN, одной строкой).
3. Закрытие: заметка-сдача в `memory/session-notes/` с матрицей верификации
   (Артефакт - Проверка - Ожидалось - Фактически - Пройдено),
   pull request в main, ревью — ваше, merge — только вы.
4. После merge — статус строки в `SESSIONS.md`: `active` -> `merged`
   (или `abandoned` с причиной, если сессия брошена).

Естественный кандидат на первую сессию — работы самого этапа
документационного контроля: инвентаризация, починка ссылок и метаданных
(то, что DEC-001 разрешает при блокировке).

## 8. Чего пакет НЕ делает

- Не правит ваши документы и не переносит их содержимое.
- Не снимает и не ослабляет `DEC-001`.
- Не выбирает технологии и не открывает работу над моделью v0.2 —
  это остаётся за вами после завершения этапа.

Вопросы по устройству рамки — в документах ядра пакета (каталог `core/`,
английский): рамка, кодификация, протокол сессий, гейты, память, адаптеры.
